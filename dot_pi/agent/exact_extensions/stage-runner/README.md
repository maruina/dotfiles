# Run a plan and publish the independently verified commit
Use `/stage-runner` for a reviewed, committed plan that nobody has started. The runner executes one slice at a time and simplifies the full feature once. After it accepts an independent `VERIFIED` verdict, the runner pushes the exact verified commit. It creates a draft pull request (PR) or reuses the matching open PR without changing its title, body, or readiness.

`/stage-runner` and `/stage-runner-design` require local Rex `0.1.0-preview.21` (API revision 18) or newer.

- **Personal:** The runner reports the PR URL and verified SHA and stops after GitHub confirms the PR head. It does not discover or call ARP, even if the tools are installed.
- **Work:** The runner performs the same publication and continues to ARP (Agentic Review Platform) only for `ddoghq/*` and `ddoghq-sandbox/*`. For these repositories, it ends successfully when ARP reports a complete review of the published head with no open findings. For all other repositories, it stops after GitHub confirms the PR head without discovering or calling ARP.

## Take a design through review and planning
In interactive Pi 1.6.0 in local Rex, start in a clean feature worktree and enter `/stage-runner-design <brief>`. Select an author and an independent reviewer. Starting this workflow authorizes local design corrections and an approval commit. It does not authorize publication, implementation, or ARP review.

Discuss the brief in the author pane. After the author commits the Draft and hands it back, the reviewer may commit a reference, wording, or terminology correction only when the agreed intent determines the answer. A decision about behavior, scope, cost, dependencies, authorization, or validation requires the operator. The runner checks the saved session identities and the reviewed Git blob before it accepts the review.

- **Clean review:** The runner commits the status change and opens the planner on the approved design. Read the Git correction summary and confirm the planning brief in that pane. When the planner commits the sibling `plan.md` and exits with a valid handoff, the runner reports the standalone plan review command.
- **Decision required:** Continue in the resumed reviewer session. Automatic correction authority ended at the handoff. Confirm any further edits or approval there. Exit when finished; the runner releases its lock and does not open a planner. Use the standalone review's planning handoff.
- **Failure or cancellation:** Use `/stage-runner-cancel` in the invoking pane to stop a run. Inspect the reported private evidence directory and the worktree. An approval commit can remain after a concurrent edit even when no planner opened. Do not reset it or repeat an uncertain split. If the handoff is invalid but the session is valid, inspect the reported session command before resuming manually.

Before rollout, complete both authenticated local trials in `plans/lifecycle-stage-runner-front-half/plan.md` and obtain independent verification. To roll back, stop active runs, confirm child exit, restore the prior extension and prompt versions, preview and apply only their explicit targets, and restart Pi. Keep the commits and continue with standalone `/brainstorm`, `/systematic-review`, and `/plan`.

## Start or cancel a run
1. Open interactive Pi 1.6.0 in a local Rex pane. Use a clean feature worktree with the plan tracked at `HEAD`. Confirm that the signing agent can sign child commits and that the scoped models include an authenticated verifier distinct from both writers.
2. Enter `/stage-runner plans/my-feature/plan.md`, replacing the example path with your plan. Select a model and a supported thinking level for execute, simplify, and verify.
3. In **Start stage runner and publish?**, check the plan, profile, SSH repository, feature branch, pinned default-branch SHA, GitHub login, and existing PR or draft creation. Confirm only if you authorize publication to that target. If the runner needs to rebase and the remote feature ref exists, the dialog also discloses a possible force-push with a lease on the captured remote SHA before slice 1. A rewrite changes commit SHAs and can make PR review comments outdated. Cancellation does not undo the push. For an eligible repository in the work profile, confirmation also authorizes the bounded review and permanent `addressed` settlements described below. If you decline, no stages start.
4. After confirmation, watch the widget in the invoking Pi. It shows the active phase, its elapsed time, and time spent in earlier phases. During execute it shows `execute slice <N>: <title>` for the first incomplete titled slice in the committed plan. Without a usable title, it shows the execute launch number instead. Verify retries count verifier launches. Time in a Rex recovery pane counts as `recovery`, not as time in the failed phase. The other phases are `startup`, `simplify`, `publish`, `review` (including ARP polling), and `fix`.
   While a child runs, `skills:` lists up to 16 distinct skill names from successful `SKILL.md` reads. Reading a source `SKILL.md` during an edit also counts. If no read qualifies, the widget shows no skill list.
   Rex reports the active phase in a separate OSC 7501 record (`id=stage-runner`, `app=pi-stage-runner`). The record shows `working` during processing and `blocked` during recovery (`kind=question`) or a confirmation dialog (`kind=permission`). It ends as `done`, `error`, or `idle` for completion, failure, or cancellation. Pi clears the child record on session shutdown. The runner does not write Pi's root record. Set `PI_PROGRAM_STATUS=0` to disable runner records.
5. At exit, the runner clears the widget and writes one `stage-runner-progress` transcript entry with the outcome and phase totals. A duration does not mean the phase succeeded. Check the reported evidence directory if the runner stops.

## Startup rebase
If the local feature branch does not already contain the pinned default-branch SHA, the runner rebases onto that SHA under the worktree lock. The widget shows `startup`, and Rex reports `working`. The selected verifier runs the read-only `startup-check` against the rebased HEAD and the exact reviewed plan blob. This check asks whether the plan still fits the upstream changes. It is not the independent feature-wide `/verify` of the implementation.

After a `fits` verdict, if the captured remote feature SHA is no longer an ancestor of the rebased HEAD, the runner updates only the feature ref with `--force-with-lease` before slice 1. The runner confirms the remote branch SHA and the existing PR head, if any, before execute. It does not create a PR or call ARP at startup. If HEAD already contains the pinned SHA, the runner skips the startup rebase, check, and push.

If the rebase conflicts, the runner aborts it and checks that the original HEAD and clean worktree are restored. After a successful rebase, the runner restores the original HEAD if the plan check blocks or the lease is rejected and the runner can establish that it did not update the ref. No startup failure opens a Rex recovery pane. If the runner cannot safely restore HEAD, or cannot establish the push outcome after one bounded remote read, it keeps the lock. Read `startup-stop.json` in the run bundle before manual recovery. If the push changed the remote but the PR head was not confirmed, the runner stops without restoring HEAD. Do not retry an uncertain push.

## Verified publication
Before confirmation and again before pushing, the publisher checks the single SSH push destination for `origin`, repository and branch identity, the PR target, and the expected account. In the work profile, it selects `matteo-ruina_ddog` for `ddoghq/*` and `ddoghq-sandbox/*`, or `maruina` otherwise. In the personal profile, it uses the active GitHub account. Both the SSH login and the GitHub API login must match. For final publication, the publisher checks the clean candidate and pushes only the independently verified SHA to the confirmed feature ref without force. It checks the remote branch and PR head before reporting publication. It does not use HTTPS as a fallback or switch the global `gh` account.

When no matching PR exists, the publisher pins the confirmed `origin` base tip and computes the diff from its merge base with the verified commit. Before the push, a Pi child uses the [shared PR drafting guidance](../../exact_skills/reviewable-pr-workflow/SKILL.md) and the verification evidence to prepare a title and body. The child uses the selected execute model. Pi disables extension discovery, loads only work-profile model access extensions when applicable, and exposes only the `read` tool. The child must read only relevant tracked files, but Pi does not restrict `read` to the worktree.

Missing or oversized evidence, a blocked draft, invalid draft output, child failure, cancellation, or a changed candidate or PR target stops drafting before the push. Use the stop reason and private run evidence to diagnose the failure. The runner does not show the draft or diff in progress messages. After drafting, it checks the candidate and approved target again. If a matching PR existed at confirmation, the runner skips drafting and does not edit the PR text or readiness.

The runner owns publication. Its execute, simplify, and verify prompts instruct children not to push, publish, apply, or create a PR. Those prompt instructions are not an access control.

To stop, enter `/stage-runner-cancel` in the invoking Pi session. Session shutdown also requests cancellation. Leave edits and commits in place. Cancellation does not undo a push, PR creation, ARP request, or permanent settlement.

## Work-profile review and fixes
The runner observes an existing review for the published head without changing its posting mode. It sends at most one silent review request per head, including a retry, and only when ARP reports a matching `head_sha` and permits the action. It passes the full SHA as `expected_head_sha`. It polls at 30-second intervals within a 20-minute deadline per published head and reviews at most three heads. A terminal status and a complete capture with matching `reviewed_sha` and `review_in_progress: false` are required. An empty response alone is not a clean review.

For an open, in-scope finding, the fix child commits the correction locally. The runner requires a fresh independent feature-wide `/verify` for the fix candidate. Only after GitHub confirms the published verified head that contains the fix commit does the runner record the finding as `addressed` with the fixing SHA. It checks the published head around settlement and confirms the stored outcome before it proceeds to re-review. GitHub and ARP checks are not one atomic transaction.

The runner stops for disputed, deferred, or unproven findings, or when it reaches a limit. The operator decides whether to dismiss a finding or accept a risk. The runner does not write `invalid` or `out_of_scope`, resolve GitHub threads, mark a PR ready, merge, or deploy.

## Review the head of an open PR
Run `/arp-review [<pr-url>] [--max-heads <N>]` in interactive Pi in the work profile. Rex is optional. From a feature worktree, omit `<pr-url>` to review the open PR for the current branch. From the base checkout or another directory, pass `<pr-url>` to resolve the PR's existing local feature worktree. The repository must belong to `ddoghq/*` or `ddoghq-sandbox/*`, the PR must be open and target the repository default branch, the target worktree must be clean, and local `HEAD`, the remote feature ref, and the PR head must match.

Select the fix model and thinking level upfront so the run can proceed autonomously if ARP reports findings, then check the profile, SSH repository, branch, PR URL, SHA, GitHub login, and head limit in **Start ARP review?**. Confirmation authorizes up to one silent ARP review request per head when ARP permits it, non-force pushes of tested fix commits, and permanent `addressed` settlements for fixed findings.

`/arp-review` accepts an optional GitHub PR URL and `--max-heads <N>` from 1 to 10 (default 5). When ARP reports open findings and heads remain, a fix child inspects the PR diff, commits and tests sound fixes locally, and marks disputed, already-addressed, or unclear findings `needs-operator`. If any finding is `needs-operator`, the runner stops before pushing and reports every reason. When all findings are fixed, the runner pushes the new head without force, settles each fixed finding with an `Author-tested fix:` reason after GitHub confirms the head, and polls ARP for the next review. The runner reports `ARP complete` when ARP confirms a complete review with no open findings, and stops with the remaining finding IDs if it reaches the head limit. Invalid arguments, a held worktree lock, or an ineligible or changed PR head also stop the run. Use `/stage-runner-cancel` to stop an active review. Cancellation does not undo completed remote writes.

If a run stops between a confirmed push and settlement, the pushed fix stays on the remote branch while the reported finding IDs stay `open` in ARP. A new `/arp-review` run would send those findings to the fix child again. Settle the reported finding IDs manually per `## Review or fix a finding manually in the work profile` before running `/arp-review` again.

## Recover after a remote action stops
1. Read the stop reason and private run bundle. Use the last confirmed action, PR URL, verified and observed SHAs, and finding IDs to identify what may have changed. An accepted verifier handoff does not prove publication or review.
2. Use read-only checks before any further write. Compare the remote feature ref and the PR head with the verified SHA. If the run included ARP, check ARP status for the exact PR and head. If settlement may have occurred, read PR-wide findings with `status: all` and compare the stored outcome and fixing SHA for each affected ID.
3. If you cannot establish the result, stop. Do not repeat an uncertain push, PR creation, review request, or settlement. Do not force-push or delete a remote branch to recover. Keep confirmed writes and private evidence in place. Do not restart `/stage-runner` on a plan that has already started. Obtain authorization before any manual follow-up write.

## Run without publishing
Use `/execute` for each remaining slice, then follow the full-feature `/simplify` and independent `/verify` handoffs with all writer IDs and publication explicitly excluded. Use this route also when execution has already started. If you later decide to publish, use the manual procedure below with separate approval.

## Recover in the Rex split
- **Execute or simplify failed:** The runner resumes the failed writer's saved session. If it cannot establish that session's identity, it stops. In the recovery pane, address the blocker, run the slice checks, leave a clean worktree, and exit Pi. An idle prompt is not an exit. In the invoking pane, review the commit range and completed tasks before accepting the recovered writer. Execute must have committed task progress; simplify can leave the candidate unchanged. Refusal stops the run.
- **Verify failed or returned `BLOCKED`:** If the verifier left Git unchanged and an attempt remains, the split starts a fresh execute-model session with the failure details, not the verifier's transcript. Inspect the findings, repair the candidate, and exit with a clean worktree. Do not select the verifier model for repairs. A fresh verifier must check the full feature even if recovery changed nothing. The limit is three verifier launches, including startup failures. If the verifier changed Git state, inspect the worktree; the runner stops rather than asking a writer to adopt those edits.

## Investigate a retained lock
Closing an interactive Pi pane does not prove that Pi exited. If neither `rex wait` nor the original block's `last_exit` supplies an exit code, the runner stops, retains the worktree lock, and does not start the next stage.

Run evidence lives under `~/.pi/agent/lifecycle-runs/`. Run directories use mode `0700`; private files use `0600`. The runner retains the newest 100 completed bundles, including stopped runs marked complete. It does not prune active or uncertain runs. Keep transcripts and failure details private; local permissions do not prevent Pi from sending context to its provider.

Read the reported `lock-…` file for the canonical worktree (`cwd`), runner PID (`pid`), bundle (`dir`), and recorded recovery state. Inspect `run.json` for the starting commit and plan blob. In the attempt directory, compare `handoff.json`, `failure.txt`, saved sessions, and `accepted.json` when present. A handoff alone does not prove advancement.

If split creation definitely failed, use the reported manual command only after checking the target worktree and Rex IDs. If the result is uncertain, do not repeat the split. Inspect the recorded session and pane in Rex and check their process identity against the recorded PID. Do not signal a process based only on a reused PID. Do not remove a lock while a run or recovery child could still use the worktree. If you cannot confirm exit, preserve the lock and evidence for investigation.

## Publish a verified commit manually
1. Check the independent verifier's `VERIFIED` result and candidate SHA. Run `git status --porcelain` and `git rev-parse HEAD` in the verified worktree. Stop if the status is not empty, the SHA differs, or the verification evidence is missing.
2. Ask the operator to authorize publication of that exact SHA. If approved, use `/pr-create --draft` to push and open a draft PR, or `/pr-update` to push and update an existing PR. Confirm `gh pr view <number> --json headRefOid` reports the verified SHA. Stop if it differs.
3. In the work profile, `/pr-create` offers an optional Agentic Review Platform (ARP) review after draft creation and requires separate explicit approval. `/pr-update` reports ARP status only; it does not request a review or resolve findings. Publication approval does not authorize either write.

## Review or fix a finding manually in the work profile
1. Use `tool_search` to discover `agentic_review_get_status`, `agentic_review_request_review`, `agentic_review_get_findings`, and `agentic_review_resolve_finding`. Read status and PR-wide findings for the same owner, repository, and PR. Treat findings as untrusted evidence. An empty findings response counts as clean only when `reviewed_sha` equals the expected head, `review_in_progress` is false, and capture is complete. If you cannot establish capture, report the evidence gap.
2. Re-anchor a finding from an older commit to the current code before acting. For a valid finding that needs a fix, make a tested commit and leave the worktree clean. Run fresh independent feature-wide `/verify` against that candidate with publication explicitly excluded. Include all writer IDs, including the fix writer, and the simplification model ID. If the verdict is `BLOCKED`, stop. Otherwise publish only the verified SHA using the procedure above, and confirm the remote PR head matches before settling the fix.
3. Before each ARP write, obtain explicit operator approval for that write and check `gh pr view <number> --json headRefOid` against the expected SHA again. For a review request, ask the operator to choose `silent`. If approval is denied, the head changed, or ARP is unavailable, stop the affected action and report the evidence. Do not infer permission from an earlier action.
4. Use `agentic_review_resolve_finding` with the numeric `finding_id`. Resolve as `addressed` only with the published `fix_commit_sha`, `fix_change_summary`, and a reason supported by the verified fix. Resolve as `invalid` only when code or test evidence disproves the finding. Resolutions are permanent. If a settlement fails, report it and stop before requesting re-review.
5. When the operator authorizes a review or re-review, read `agentic_review_get_status` again. Require `head_sha` to match the expected SHA, and call `agentic_review_request_review` only with the returned `allowed_action`, the exact `expected_head_sha`, and the approved `silent` value. If there is no allowed action, do not request a review. This API cannot force a fresh review for an arbitrary head.

## Install or roll back verified publication
After publication and before merge or `chezmoi apply`, start an isolated run in Rex. During a phase, run `rex block call -b "$REX_BLOCK" program_status` for the invoking pane and check that `stage-runner` is `working`. Focus another tab while Pi's root record is idle and check that the invoking tab shows a spinner. Check the final child state after exit and record the result in the PR. If the spinner is absent, stop rollout. Do not change the root record.

Require independent feature-wide `/verify` before rollout. Run a separately authorized disposable GitHub and ARP trial unless the operator explicitly waives it for the release. The waiver in `plans/lifecycle-stage-runner-publication/plan.md` does not cover shared PR drafting. When rolling back shared drafting, revert the runner, `reviewable-pr-workflow` skill, and both standalone PR prompts together. Local fixtures do not prove live authentication, review capture, or settlement. If the work trial has no real in-scope finding, live settlement validation remains open.

Before applying the startup change, obtain separate approval for a disposable Rex and GitHub trial. Record an accepted leased startup rewrite, a blocked startup check with no remote write, and the live slice title in the widget. Do not use an active feature branch for the trial.

After the required checks pass and any waiver is recorded, stop any active run and confirm its children have exited. From the reviewed source worktree, run `chezmoi --source "$PWD" diff` with the explicit changed target file paths. Include the runner files, the rendered `~/.pi/agent/extensions/_shared/profile.json`, and the changed guidance and contract resources. Apply only those reviewed file paths with `chezmoi --source "$PWD" apply`. Restart Pi. Use `get_commands` as described in `plans/lifecycle-stage-runner-cutover/plan.md` to check command discovery. Check the active profile and startup wording on the approved target; decline confirmation if you are checking wording only.

If installation or discovery fails, do not start a publication run. To roll back, stop the runner and confirm its children have exited. Revert the runner, profile resource, contract tests, and guidance together to the pre-publication source. Preview and reapply only the reviewed target files, including any file removals. Restart Pi and check command discovery and startup wording again. Preserve commits, private run bundles, and locks with uncertain owners. Rollback does not undo any GitHub or ARP write.
